# Кэширование

Беру данные, которые ходят по системе из [15-clients-and-scenarios.md](../15-clients-and-scenarios.md), и раскладываю их по точкам кэширования: браузер, CDN/edge, сервер, не кэшируем. Слой входа тут уже описан в [16-entry-layer.md](../16-entry-layer.md) - там короткий кэш снапшота на шлюзе уже упомянут, здесь разбираю его и всё остальное подробно.

Главное ограничение задаёт [ADR-01](../adr/01-functional-suitability-over-performance.md): клиент видит только согласованную версию состояния. Значит кэш нигде не имеет права склеить кусочки от разных версий - либо кэшируем версию целиком, либо не кэшируем вовсе.

Разбито на три части:

- [01-data-and-points.md](01-data-and-points.md) - какие данные вообще есть и в какой точке кэшируется каждая группа
- [02-invalidation.md](02-invalidation.md) - стратегия инвалидации по каждой группе и почему именно такая
- [03-backend-questions.md](03-backend-questions.md) - что придётся уточнить у бэкенда, потому что заголовки выдаёт он

Если совсем коротко, то решений тут три: статику с хешом кэшируем навсегда и инвалидируем сменой имени, всё живое вокруг матча живёт на коротком TTL и умирает само, а лента событий переезжает из `no-store` в `immutable` в момент финального свистка.
