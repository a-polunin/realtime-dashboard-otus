### Context

Нужно решить, как устроен слой входа: клиенты стучатся в сервисы напрямую, через один API Gateway, или через отдельные BFF под каждый тип клиента.

Клиентов три ([15-clients-and-scenarios.md](../15-clients-and-scenarios.md)): веб-дашборд(SPA), мобильное приложение на React Native и партнёрская интеграция(B2B API). Веб и RN хотят одно и то же - снапшот согласованной версии состояния плюс поток обновлений, - и ходят по одному контракту ([14-degradation-map.md](../14-degradation-map.md)). Партнёр хочет те же данные, но пуллом, пачками матчей и с лимитами по тарифу.

Ключевой факт: агрегация под клиента у нас уже сделана внутри домена. [Сервис состояния матча](../05-service-boundaries.md) собирает согласованную версию, и в [ADR-01](01-functional-suitability-over-performance.md) мы обещали, что клиент видит только её. То есть классической причины для BFF - "клиент сам ходит в пять сервисов и склеивает ответ" - здесь нет.

Проверяю тем же фреймворком из трёх вопросов, что в [ADR-02](02-monolith-frontend-single-repo.md):

1. Есть ли граница команд, которую надо закрепить отдельным раннтаймом? Нет, автор один.
2. Нужно ли деплоить слой входа для веба и для мобильного независимо? Нет, контракт у них общий, разъезжаться ему пока не с чего.
3. Окупает ли изоляция BFF свою цену? Нет: BFF стал бы вторым местом, которое собирает картинку матча, а размазывать гарантию из ADR-01 по двум местам мы договорились не делать.

### Decision

Один API Gateway на все три клиента, отдельных BFF не заводим.

Конкретно:

1. На шлюзе живёт только то, что не требует знания домена: TLS и роутинг, версия публичного API, аутентификация, rate limiting и квоты по тарифу, WS/SSE upgrade и распределение соединений, короткий кэш снапшота, trace id, отсечение аномального трафика.
2. Шлюз не склеивает ответы: каждый запрос уходит ровно одному сервису - поток версий в доставку клиентам, снапшот и история в состояние матча.
3. Партнёрский B2B API - это отдельный публичный путь на том же шлюзе со своими лимитами, а не отдельный сервис.
4. Доменные решения остаются в сервисах: согласованность версий, подписки и досыл с последней версии, доступность матча по тарифу, выбор источника, пересчёт метрик, обратная совместимость формата событий.

### Consequences

**Положительные**

- Гарантия из ADR-01 по-прежнему проверяется в одном месте - в сервисе состояния матча, а не в домене и в BFF одновременно.
- Ноль дополнительной инфраструктуры на слое входа: нет отдельного раннтайма, пайплайна и контракта между BFF и сервисами.
- Общие для всех клиентов вещи(аутентификация, лимиты, приём пика подключений на старте матча) сделаны один раз до домена, а не шесть раз внутри сервисов.
- Кэш снапшота на шлюзе снимает с сервиса состояния матча тысячу одинаковых запросов на старте матча(D2/S2).

**Отрицательные**

- Клиенты получают ровно тот ответ, который отдаёт домен: если мобильному понадобится урезанный payload ради трафика, добавить его надо будет в контракт сервиса, а не в свой BFF.
- Шлюз - единая точка отказа для всех трёх клиентов, и его конфигурация(лимиты, роуты) становится частью релизного риска.
- Есть риск ползучей логики: любая "маленькая склейка двух ответов" на шлюзе превращает его в BFF без ADR. Признак, по которому это ловим - шлюзу понадобилась своя БД или знание про версии и метрики.

**Отвергнутые**

- **BFF на каждый клиент(web-BFF, mobile-BFF, partner-BFF).** Два фасада над одним и тем же ответом для веба и RN плюс третий над теми же данными для партнёра - цена в три раннтайма за нарезку, которая пока одна на всех.
- **Клиенты ходят в сервисы напрямую, без шлюза.** Тогда аутентификация, лимиты и приём WS-пика расползаются по шести сервисам, а публичный контракт оказывается прибит к внутренним границам - двигать сервисы, не ломая клиентов, станет нельзя.

### Пересмотр

Возвращаемся к вопросу, если контракты веба и мобильного разъехались, партнёрам понадобилась своя агрегация, которой нет ни у одного клиента, или появилась вторая команда со своим темпом релизов слоя входа.
