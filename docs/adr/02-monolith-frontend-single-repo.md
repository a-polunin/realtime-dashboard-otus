### Context

Нужно решить, как раскладывать код фронтенда по репозиториям: monorepo (общий воркспейс с несколькими пакетами и build-оркестрацией типа Nx/Turborepo), микрофронтенды (несколько самостоятельно собираемых и деплоящихся кусков UI, склеенных в runtime) или простой монолит - один пакет, один репозиторий, один бандл.

У меня один фронтенд-пакет (SPA) с четырьмя фичами - `live-score`, `match-charts`, `event-history`, `ws-subscription` - и раскладка внутри уже плоская, без FSD ([11-frontend-architecture.md](../11-frontend-architecture.md)) ровно по той же причине, что здесь: автор один, границы держатся в голове, формальная дисциплина импортов пока ничего не страхует.

Бэкенд уже разбит на 6 сервисов по границам ответственности ([05-service-boundaries.md](../05-service-boundaries.md)), и это разделение живёт на уровне деплоя и владения данными, а не на уровне репозиториев - вопрос monorepo/polyrepo для бэкенда этим документом не закрываю, ADR только про фронтенд.

Использую для решения простой фреймворк из трёх вопросов - если хотя бы один даёт твёрдое "да", дробим, если ни один - остаёмся монолитом:

1. Есть ли граница команд, которую нужно закрепить границей репозитория/раннтайма?
2. Есть ли реальная потребность деплоить и откатывать части независимо друг от друга?
3. Окупает ли выгода от формальной изоляции (monorepo-тулинг, отдельные раннтаймы микрофронтендов) цену координации, которую он вносит?

По всем трём - нет:

1. Команда - один человек, границу между "командами" рисовать не на чём.
2. CI/CD собирает и льёт на CDN один статический бандл ([10-cicd.md](../10-cicd.md)), отдельного релизного цикла ни для одной из четырёх фич не требуется - нет сценария "откатить `match-charts`, не трогая `live-score`".
3. Monorepo-тулинг (Nx/Turborepo, версионирование пакетов) решает проблему многих пакетов и многих команд - у меня один пакет. Микрофронтенды решают проблему независимого деплоя/раннтайма разных команд - у меня один раннтайм и один автор. Оба инструмента добавили бы координационную цену (общие раннтайм-контракты, shared-deps версии, лишний CI) без единой выгоды, которая бы её окупила.

### Decision

Один простой репозиторий, один фронтенд-пакет, один SPA-бандл. Никакого monorepo-тулинга и никаких микрофронтендов.

Конкретно:

1. Frontend остаётся одним пакетом с плоской раскладкой по фичам ([11-frontend-architecture.md](../11-frontend-architecture.md)) - решение этого ADR её не меняет, только подтверждает на уровне репозитория.
2. Изоляция, которая реально нужна (отдельный чанк для `match-charts`, лениво загружаемый роут для `event-history`), уже получена code splitting'ом внутри одного бандла ([09-rendering-model.md](../09-rendering-model.md)) - без цены отдельного раннтайма или отдельного деплоя.
3. Разделение ответственности бэкенда живёт там, где для него есть реальная причина - на границах сервисов и данных ([05-service-boundaries.md](../05-service-boundaries.md)), а не продублировано ещё раз на фронтенде через микрофронтенды.

### Consequences

**Положительные**

- Ноль дополнительной инфраструктуры: нет отдельных пайплайнов на фичу, нет shared-runtime контрактов между кусками UI, нет version skew между пакетами monorepo.
- Один бандл - предсказуемый деплой и откат: откатывать/раскатывать всегда всё приложение целиком, без вопроса "а что если версии двух микрофронтендов разошлись".
- Решение согласуется с [11-frontend-architecture.md](../11-frontend-architecture.md) - в проекте один принцип "не дробим то, что некому и незачем дробить", а не два разных на соседних уровнях.

**Отрицательные**

- Если появится вторая команда или партнёрская интеграция, которой нужен только `live-score` как встраиваемый виджет с собственным релизным циклом - придётся выделять его в отдельный деплоящийся кусок постфактум, а не с нуля.
- Весь фронтенд собирается и тестируется как одно целое - при росте числа фич время CI на весь пакет будет расти линейно, частичной пересборки не будет.

**Отвергнутые**

- **Monorepo с несколькими пакетами.** Правило "monorepo даёт единый CI и общий тулинг" ничего не экономит, когда пакет один - это просто репозиторий с одним пакетом, только с лишней конфигурацией workspace-менеджера сверху.
- **Микрофронтенды.** Их цена (отдельные раннтаймы, тестирование этих фронтов, оркестрация сборки в один экран) окупается только при нескольких командах или потребности в независимом деплое - здесь нет ни того, ни другого.
