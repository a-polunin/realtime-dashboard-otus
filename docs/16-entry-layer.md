# Слой входа: шлюз и BFF

Разбираюсь, что стоит между клиентами из [15-clients-and-scenarios.md](15-clients-and-scenarios.md) и шестью сервисами из [05-service-boundaries.md](05-service-boundaries.md): нужен ли отдельный BFF и что забирает на себя шлюз. Схема получившегося слоя входа - в [views/entry-layer](views/entry-layer/entry-layer.md).

## Нужен ли отдельный BFF

Отдельный BFF не заводим. Разбираюсь почему.

BFF обычно берут, когда клиенту приходится самому ходить в пять сервисов и склеивать ответ у себя: тогда логика агрегации расползается по клиентам, а мобильный ещё и платит за это лишними round trip'ами. У нас такой проблемы нет: собирать состояние из событий и метрик - это работа [сервиса состояния матча](05-service-boundaries.md), и в [ADR-01](adr/01-functional-suitability-over-performance.md) мы прямо обещали, что клиент видит только согласованную версию. То есть агрегация под клиента уже сделана внутри домена, и BFF было бы вторым местом, которое собирает картинку.

Второй обычный повод для BFF - разным клиентам нужна разная нарезка данных. Веб и RN у нас ходят по одному контракту и хотят одно и то же(снапшот + поток версий), так что нарезка одна на двоих. Заводить BFF на каждый клиент только потому, что клиентов два - это два фасада над одним и тем же ответом.

С партнёрским API интереснее: у него другой профиль(пулл вместо потока, пачки матчей, тарифы и лимиты) и меняться он будет по другим причинам. Но нужный ему ответ - это те же версии состояния и та же лента событий, просто в другой упаковке и с другими лимитами. Упаковка и лимиты - это как раз то, что умеет шлюз, поэтому пока это отдельный публичный путь на шлюзе, а не отдельный сервис.

Когда решение стоит пересмотреть:

- контракты веба и мобильного разъехались настолько, что один ответ обоих больше не устраивает;
- партнёрам понадобилась своя агрегация, которой нет ни у одного из наших клиентов(например свои сводки по турниру за сезон) - вот тогда это отдельный BFF;
- появилась вторая команда, которой нужен свой темп релизов

Решение зафиксировано в [ADR-03](adr/03-entry-layer-gateway-without-bff.md).

## Что выносим на шлюз, а что оставляем сервисам

Правило, по которому делю: на шлюз идёт то, что одинаково для всех запросов и не требует знания домена. Как только для решения нужно знать, что такое матч, версия или xG - это уже сервис.

**Шлюз (API Gateway):**

| Что                                                             | Почему здесь                                                                     |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| TLS-терминация, сжатие, CORS                                    | Инфраструктура, одинаковая для всех трёх клиентов                                |
| Роутинг по публичным путям и версия публичного API(`/v1/...`)   | Один вход, за которым можно двигать сервисы, не ломая клиентов                   |
| Аутентификация: проверка токена, отсечение анонимов             | Один и тот же токен у веба, RN и партнёра, шесть раз это проверять незачем       |
| Rate limiting и квоты по тарифу                                 | Это [Возможность 7](04-capabilities.md), generic-функциональность, берём готовое |
| WS/SSE upgrade и распределение соединений по инстансам доставки | Пик на старте матча(D2/S2) надо принять до домена                                |
| Короткий кэш снапшота матча                                     | Тысяча клиентов на старте матча просит один и тот же снапшот                     |
| Присвоение trace id и общие метрики запросов                    | Иначе трейсинг начинается с середины системы                                     |
| Отсечение аномального трафика                                   | Защита всего, что за шлюзом, а не конкретного сервиса                            |

**Сервисы:**

| Что                                                       | Почему не на шлюзе                                                                                                                         |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Согласованность версии состояния                          | Обещание из [ADR-01](adr/01-functional-suitability-over-performance.md), живёт в одном месте - в сервисе состояния матча                   |
| Подписки и досыл с последней известной клиенту версии     | Надо знать, что такое версия матча, и помнить, кто на чём остановился - это состояние доставки, а не шлюза                                 |
| Какие матчи доступны этому тарифу                         | Шлюз проверяет, что клиент вообще имеет право стучаться и не превысил лимит. Доменное "этот матч в твой тариф не входит" - решение сервиса |
| Выбор источника и пометка _устаревшие_(S1)                | Доменное решение, шлюз про провайдеров ничего не знает                                                                                     |
| Пересчёт метрик и компенсация отмен                       | Ядро, к слою входа отношения не имеет                                                                                                      |
| Совместимость формата событий для старых мобильных версий | Обратная совместимость контракта - обязанность владельца контракта, шлюз чужие поля переписывать не должен                                 |

Чего на шлюзе не будет: сборки ответа из нескольких сервисов, знания про xG и версии, своей БД. Как только шлюз начнёт что-то склеивать - он и станет тем самым BFF, который мы решили не заводить.
