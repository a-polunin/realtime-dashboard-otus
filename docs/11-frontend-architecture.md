# Архитектура фронтенд-кода

## Что выбираем

FSD не берём. Раскладываем код по фичам плоско: `app / pages / features / shared`, без слоёв `entities`/`widgets`/`processes` и без слайсовой структуры (`ui/model/api` внутри каждой папки).

Почему не FSD: у FSD есть одна реальная выгода - дисциплина импортов между слоями, которая окупается, когда фич много и/или людей несколько, потому что без формального правила кто-то рано или поздно долезет через границу, которую никто явно не проверяет. У нас фич четыре (`live-score`, `match-charts`, `event-history`, `ws-subscription`), автор один - и весь код у него в голове, границы держатся конвенцией без линтера слоёв, никакого риска тут страховать не нужно.

Границы между фичами при этом уже есть - но это не заслуга FSD, а следствие [09-rendering-model.md](09-rendering-model.md): графики отдельным чанком, история событий отдельным лениво загружаемым роутом. Любая структура, хоть плоская, хоть слоёная, получила бы ту же нарезку. Тащить сверху ещё и терминологию FSD (слайсы, публичный API через `index.ts`, отдельный слой `entities` под три небольших типа) - это оверкил какой то.

## Слои и что в них лежит

```
src/
  app/
    providers/         # роутер, тема, bootstrap WS-подключения
    router/
  pages/
    match.tsx           # первый экран: счёт + лента событий, без ленивой загрузки
    match-history.tsx    # лениво загружаемый роут - Возможность 3 (04-capabilities.md)
  features/
    live-score/          # счёт, часы, лента ключевых событий - первый экран
    match-charts/        # xG/владение/точность передач + чарт-либа, отдельный чанк
    event-history/       # полная лента + отмены через VAR
    ws-subscription/     # подписка на канал матча, реконнект - Возможность 6
  shared/
    api/                  # запрос снапшота, WS-клиент
    types/                # Match, Event (включая компенсирующие отмены), Metric - общие типы
    ui/                   # кнопки, лейаут, токены
    lib/                  # утилиты
```

Типы Match/Event/Metric ([Возможность 3, 4](04-capabilities.md)) переиспользуются в паре мест (событие - и в live-фиде, и в истории), но их три штуки и они маленькие - хватает `shared/types`, отдельный слой под них не нужен.

## Когда пересмотреть

Если фич станет заметно больше (5-10+) или в проекте появится больше одного разработчика, дисциплина "все правильно импортируют, потому что помнят" перестанет работать сама - тогда стоит вернуться к вопросу и, возможно, взять что-то вроде FSD именно за формальные границы, а не за красоту схемы.

## Что не сюда

Auth, метрики, трейсинг ([Возможность 7](04-capabilities.md)) - это обычно готовые SDK, подключаются в `app/providers`, отдельной папки под generic-функциональность не заводим.
